# vllm-plugin-fl 详细实施与验收流程

仅适用于本 profile。继承 [通用工作流](../../docs/model-adaptation-workflow.zh-CN.md)；历史直接平台目录沿用其原路径。

3. **进行适配。** 结合模型结构与推理链路分析、用户指定平台的环境分析，以及用户提供
   的适配相关参考文件，按照以下子步骤完成适配：

   1. **制定 plugin 适配方案。** 基于模型结构与推理链路分析、平台环境分析和用户提供的
      参考文件，将每个模型组件、推理阶段、关键算子、并行要求和运行依赖映射到当前
      plugin 路径及目标平台能力。在平台环境分析或对应编号适配问题中建立差距清单，
      逐项写明需要修改的 plugin 位置、算子来源、对 `eager`/`graph` 的影响、
      依赖、风险和计划验证方式。该文档属于适配准备上下文，不属于问题记录。
      选型前阅读 `docs/plugin-contribution-policy.md` 和目标插件 checkout 当前的设计/贡献
      规范。说明职责归属、接口契约、替代方案、共享调用方、可选依赖、守卫、默认行为及
      有依据的代表性回归范围。
   2. **固定基线并明确修改边界。** 在正在运行的适配容器内，修改前记录 plugin、vLLM
      和 FlagGems 的仓库路径、revision、分支及工作区状态。核实已安装 Plugin 实际解析到
      该 editable 源码后，直接在该源码中完成必要产品修改，不得在远端工作根目录建立或
      使用第二份 checkout；整个适配过程中 vLLM 源码必须保持只读且不得产生任何改动。禁止停止、重启或删除
      适配容器。保存 vLLM 修改前后的 revision 与工作区状态证据；基线和环境事实放入
      `environment/environment-analysis.md`。
      如果工作区不干净、revision 不一致或修改边界被破坏成为适配问题，则在
      `adaptation/` 下建立编号 Markdown 问题记录。
   3. **接入算子前同步 FlagGems。** 检查或接入任何 FlagGems 算子前，先把正在运行的
      适配容器内 FlagGems 仓库更新到预期跟踪分支的最新 commit。首先按远端工作目录
      前置条件核实该现有 checkout 的写入授权。没有授权或无法核实其身份时暂停同步并
      报告阻塞，不得搬迁已有仓库，也不得在工作根目录另建替代 checkout。
      更新前记录 remote、
      分支、upstream、revision 和工作区状态。只有工作区干净且目标分支与 upstream 明确
      时才能更新；先 fetch，再使用仅允许 fast-forward 的 pull，禁止 reset、强制更新或
      丢弃本地改动。将同步命令和更新后的 revision 记录到平台环境分析或对应编号问题中。
      如果同步无法完成，应报告准确阻塞原因，
      在 `adaptation/` 下建立编号问题记录，且不得继续基于旧 revision 选择算子。
   4. **接入 FlagGems 已有算子。** 对 plugin 尚未调用或不支持的每个算子，检查 plugin
      的 dispatch/backend 设计和同步后的 FlagGems revision。如果 FlagGems 已有兼容
      实现，应遵循 plugin 现有架构补齐 dispatch、backend、注册或平台绑定，不得以临时
      直接调用绕过 plugin 设计。补充针对性的接入与数值测试。当这项工作解决了兼容性
      缺口或故障时，在 `adaptation/` 下对应的编号 Markdown 问题记录中写明 FlagGems
      符号、revision、plugin 入口、支持约束、解决方法和测试结果。
   5. **实现 FlagGems 缺失算子。** 如果同步后的 FlagGems revision 没有兼容实现，
      则在 plugin 内新增 Triton 算子，并通过相同的 plugin dispatch 框架接入。Triton
      实现必须兼容 `graph` capture/replay，而不能只支持 `eager`；应避免 capture 阶段
      的主机同步、不受支持的动态内存分配、依赖数据的主机控制流，以及不稳定的张量
      shape 或地址。补充数值、dtype、shape、layout、设备、边界条件和执行模式测试，
      并单独覆盖 `eager` 与 `graph` capture/replay。记录所检查的 FlagGems revision 和
      检索证据，明确标注该算子在 FlagGems 中缺失，并在 `adaptation/` 下的编号
      Markdown 问题记录和最终 `acceptance/adaptation-summary.md` 中写明 Triton 实现
      位置、支持约束、plugin 接入方式、测试结果和尚存限制。
   6. **整理可复现的 FlagGems 算子问题。** 在适配任一阶段，如果 FlagGems 算子出现报错
      或数值精度问题，在已批准远端根目录的 `07-bugs/` 中为该问题保留独立目录，并通过
      `container_root` 下已核实的对应路径原地执行。如果用例已经存在且容器可以从该路径
      访问，不得再复制、重建或同步到容器 `/bug`。只有必要工具或上游复现流程明确要求
      `/bug` 路径时，才可把同一个 `07-bugs/` 目录以用户批准且已核实的映射暴露为 `/bug`，
      或使用用户明确批准的目录外例外；不得维护第二份副本。既无映射也无例外时，仅暂停
      依赖 `/bug` 的操作并报告所需批准，不得自动建立挂载或搬迁文件。不得把该目录创建在当前
      管理仓库、FlagGems 仓库、plugin 仓库或 vLLM 仓库的根目录。应在同一适配镜像环境中向算子开发人员提供
      能够准确复现问题、可独立执行的最小单元测试。优先直接测试 FlagGems 算子，不应要求
      启动完整模型服务，也不应依赖 vLLM 或 plugin；如果问题只会通过 plugin dispatch、
      graph capture/replay 或其他必要集成链路触发，则保留能够触发问题的最小链路，并在
      可能时提供直接调用算子的对照测试。固定随机种子，准确记录容器镜像与容器名称、
      FlagGems revision、平台、设备、软件环境、算子参数、dtype、shape、stride/layout、
      执行模式、复现命令、预期行为、实际行为、误差阈值，以及精简的报错或数值差异证据。
      如果问题与执行模式有关，应分别覆盖 `eager` 和 `graph`；精度问题必须提供可信参考
      实现或预期输出。必须在受影响主机的容器内通过工作根 `07-bugs/` 的已核实对应路径执行
      并验证测试可以稳定复现；确实需要 `/bug` 时，再核实已批准映射或用户明确例外覆盖的
      准确位置。同时在对应平台 `adaptation/`
      下对应的编号 Markdown 问题记录中写明已批准的主机存储路径、容器内问题目录、
      实际使用的 `/bug` 映射或例外（如有）以及复现命令。
      创建或验证复现用例时不得停止或重启适配容器，也不得在复现目录中存放模型权重、秘密、
      大型日志或与该问题无关的适配产物。
   7. **完成运行配置与集成。** 将并行策略、内存行为、执行阶段、模型配置和启动参数映射
      到目标平台。在不修改 vLLM 源码的前提下，补齐可复现的 plugin 侧配置、包装脚本、
      启动脚本和优化设置。只有必要的生产实现及可长期维护的 plugin 回归测试保留在正在
      运行的适配容器内 plugin 仓库中；一次性的过程脚本和代码放在已批准根目录的
      `02-issues/` 或 `05-tmp/`，且位于源码仓库之外。中间运行配置保存在远端根目录的
      `01-environment/`，不得把中间脚本称为最终启动脚本；验收确定最终 graph 配置后，将其
      可执行入口放在远端根目录顶层的 `start-model.sh`。最终脚本必须从已验收启动命令的
      最小集合构建：删除诊断、profiling、trace、dump、临时路径、过期 workaround、重复
      默认值、实验性调优项及与当前模型或平台无关的设置，除非受控验收能够证明仍然需要。
      应重新整理为最小生产启动命令，不得直接复制最后一次诊断、精度或性能测试命令，尤其
      不得保留性能测试专用的 `--no-enable-prefix-caching`。显式固定不会影响行为和可复现性
      时应使用引擎默认值，不得仅因某参数曾出现在历史命令中就继续保留。每个保留的环境变量
      和参数都必须说明其正确性、安全性、写入位置或可复现性依据；为
      避免默认值漂移而显式固定默认参数时，也必须记录理由。
      在对应的编号问题记录中引用容器内准确路径、分支、revision 或 commit、验证命令和结果，
      不得把这些产物复制到 `adaptation/`。启动模型服务时，不得把
      `--max-model-len` 设置得过小；应先根据模型配置和实现确认模型实际支持的最大上下文
      长度。如果最大支持长度大于 50000 token，初始服务配置使用 50000；如果最大支持长度
      小于或等于 50000，则使用模型实际支持的最大长度。无法确认最大支持长度时，不得猜测，
      应先完成核实，不得为掩盖内存、graph capture 或运行时问题而静默调小该值。把判断
      依据、计算结果、最终启动参数和远端配置准确路径记录到 `environment/environment-analysis.md`；如果上下文长度
      配置导致或解决了问题，还要在对应的编号问题记录中写清判断过程。
   8. **分层递进验证。** 依次验证 import 与注册、单算子、组件组合、最小模型执行，最后
      拉起完整服务。每次修改后先运行最小相关回归，并在适用时覆盖 `eager` 与 `graph`
      行为；较小范围测试未通过时，不得继续更大范围测试。
   9. **控制适配服务生命周期。** 因配置变更、故障恢复或验证需要时，只能停止或重启当前
      适配任务的推理服务或相关进程。禁止停止、重启或删除适配容器本身。操作前必须准确
      确认服务或进程，不得影响共享或无关服务。
   10. **整理可复现问题记录。** 使用 `adaptation/README.md` 作为问题索引，每个实质性
      问题使用一个编号 Markdown 文件。每条问题记录必须包含现象、影响范围、证据、诊断、
      受控尝试、根因或当前假设、解决方法或 workaround、验证结果、限制和下一步。命令和
      精简证据片段可直接嵌入问题 Markdown。必要的 plugin 实现和可维护回归测试留在 plugin
      仓库的已授权写入范围内；远端一次性过程脚本和代码留在已批准根目录的 `02-issues/`
      或 `05-tmp/`，且位于源码仓库之外；远端配置、原始日志和其他制品留在上述根目录的
      对应子目录，并通过准确路径、适用时的 revision 或 commit、命令和结果
      进行引用。进入验收前，在对应问题记录中补齐服务停启记录、FlagGems 证据以及 vLLM
      始终未改动的证明。
   11. **审查插件设计与最终 diff。** 在对应编号问题和最终验收总结中记录审查结论，
      按 `docs/plugin-contribution-policy.md` 核对已确认的 PR base、实际 HEAD、dirty/新增
      文件、既有改动归属、多模型/多平台影响、回归证据和 workaround 退出条件。设计阻塞
      未解决不能标记适配完成；实质变更后更新受影响的审查。设计审查不等于未测试平台
      已支持或完整验收已通过；未经用户明确要求不提交、推送或创建 PR。
4. **适配验收。** 完成以下全部验收工作：

   1. **执行模式验收。** 模型必须同时跑通 `eager` 模式和 `graph` 模式。本项只验证两种
      执行模式都能够成功运行；通过后，后续所有验收工作，包括小批量预检、正式精度评测、
      性能评测或 Profiling，以及适用时的通信验证，统一使用已经通过的 `graph` 模式服务
      配置。无需在 `eager` 模式下重复进行精度或性能验收。
   2. **10 并发小批量精度与性能预检。** 正式精度评测前，对每个需要验收的服务配置使用
      一组固定的简单请求，针对已验收的 `graph` 模式服务配置以 10 并发发起小批量验证。
      逐条对照预期结果检查回复，并记录错误、超时、时延、吞吐、加速卡利用率和显存/内存
      使用情况，以识别明显的性能回退。
      如果出现回复错误，先回到适配阶段修复精度；如果回复正确但性能明显异常，必须先
      定位并修复性能问题，再运行全量精度评测。每次修复后都要重新执行本项预检；只有
      精度和性能预检都通过后，才能继续下一项。
   3. **正式全量精度评测。** 在目标机器上，根据目标平台选择进入基于
      `harbor.baai.ac.cn/flageval/flageval-llmeval:v1` 或
      `harbor.baai.ac.cn/flageval/flageval-llmeval:arm64` 镜像的容器，使用
      `test/Accuracy_test/llmrun.py` 对已验收的 `graph` 模式服务执行；除非用户明确要求，
      不得替换为其他评测入口。
      准备模型专用的 `llm_config.json`，先使用 `--preflight-only` 运行 `llmrun.py`，再
      启动正式评测。冻结配置可以包含一个或多个 FlagEval/lm-eval task；每个 task 都必须在
      运行前冻结精确指标阈值和完整样本数，多 task 使用按 task 映射的样本数，并可配置按
      task 映射的数据集 path/name/split。GPQA 只是受支持的配置之一，不是唯一正式数据集。
      如果不同数据集需要不同生成参数或聊天模板，必须拆分为独立冻结配置和独立 run。
      正式全量精度评测的请求并发数必须大于或等于 32；10 并发只适用于
      前面的小批量预检。以 32 或已经验证安全的更高并发开始，在资源和服务稳定性允许的
      前提下提高并发，尽量缩短评测时间。不得为了速度牺牲结果有效性、完整样本覆盖或
      服务稳定性。如果 32 并发无法可靠运行，应先诊断并解决阻塞，不得静默降低到 32
      以下进行正式验收。在 `acceptance/` 中记录配置并发数、观测到的实际有效并发、调优
      依据、吞吐、总耗时、错误和超时情况。
      核对预期样本数、进程完成状态、最终结果与样本文件、精度指标、超时
      数量和明确的通过标准。完整评测结果有效，且每个运行前冻结的精度指标都达到配置
      阈值后，即可把正式精度子步骤标记为 `passed` 或 `complete`。精度指标不要求达到
      `1.0`，允许存在少量答错题目；不得把前置 sanity 的“逐题全部正确”要求套用到正式
      精度评测。最终超时的请求按失败/错误样本处理，必须保留在完整样本集合及指标分母中，
      不得丢弃、忽略或用重试掩盖；只要全部冻结指标仍达到阈值，允许存在少量此类超时。
      缺失或无效样本、非超时的请求/执行错误或任一指标低于阈值时，仍不能判定通过。
   4. **最终性能评测。** 只有第 3 项正式精度评测完成并达到通过标准后，才能使用
      `test/perf_test/` 基于同一套已验收的 `graph` 模式配置开始最终推理性能测试或
      Profiling。全量精度评测尚未完成或未通过时，不得启动正式性能评测。小批量验证、
      精度测试及其他非性能测试必须保持前缀缓存开启。在任何性能或 Profiling 请求开始前，
      切换到性能测试专用服务启动配置，并在本轮被测的准确服务实例启动命令中加入准确参数
      `--no-enable-prefix-caching`，并从生效的启动配置和启动证据核实该参数及关闭状态；调用
      benchmark 前把准确参数和证据引用绑定到正式性能回执。benchmark 客户端本身不负责
      修改模型服务；其 `--random-prefix-len 0` 只定义 workload，不能证明服务端前缀缓存
      已关闭。状态为开启或无法核实该准确参数已生效时，不得执行性能测试，也不得接受其
      结果。不得把该参数写入通用 graph 配置；后续继续进行非性能测试前必须恢复为开启
      前缀缓存的普通服务配置。在与平台相关
      时，使用 `test/nccl_test/` 验证通信
      能力，通信验证也应基于 `graph` 模式验收配置。
   5. **验收证据记录。** 在平台的 `acceptance/` 目录中写明准确的测试脚本、配置、数据
      集或用例集、服务模式、容器名称与镜像、执行命令、环境、结果位置、指标、通过标准
      和最终结果，并明确标注第 1 项之后的所有验收均使用 `graph` 模式。远端新增数据集/
      缓存和原始输出分别保留在已批准远端根目录的 `06-cache/` 和 `04-runs/`；已有外部数据集
      可以只读引用。本地记录路径和精简证据，不全量复制远端输出。如果公共测试文件
      需要模型专用修改，应在已批准远端 `03-acceptance/`
      中放置副本或包装脚本，不得静默修改公共基线。
   6. **最终适配总结。** 创建或更新
      `models/<model-name>/<platform>/frameworks/vllm-plugin-fl/acceptance/adaptation-summary.md`，总结适配范围、
      环境、参考文件、实施变更、可复现流程与配置、正确性和性能验证、遇到的问题及解决
      方案、最终状态、尚存限制和下一步计划。标记完成前，核实每个目标 `host_root` 顶层均有
      可执行 `start-model.sh`，其已核实容器路径能够启动最终通过验收的 graph 配置，日志/结果
      写入 `04-runs/`、缓存写入 `06-cache/`，且不影响无关服务和适配容器。总结中记录宿主机
      与容器路径、SHA-256、语法检查、实际启动/就绪结果、完整参数、revision 和验证日期。
      同时确认诊断和性能测试专用参数均已移除，并记录最小参数审查结果，以及每个保留显式
      设置的必要性依据。
      只有全部验收项及最终启动脚本验证均通过，且该文档准确反映已验证结果后，才可以将
      适配任务视为完成。
