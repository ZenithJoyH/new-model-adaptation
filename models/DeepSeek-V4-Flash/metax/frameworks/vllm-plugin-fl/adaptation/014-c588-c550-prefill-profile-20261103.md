# C588-5 与 mx-103 的 16K prefill 多 rank trace 对比

## 范围与方法

- 日期：2026-11-03；用户明确要求比较 CPU、prefill 算子与 MCCL 耗时。
- 范围：`mxC588-5`、`mx-103` 的 `deepseekV4-flash` 容器，单机 TP8，各自采集全部 8 个 rank。不是跨主机分布式推理，不启动通信 benchmark。
- Profile：`vllm-plugin-fl`；独立诊断，不执行正式验收，不改变旧 `framework.yml` 的 mx-59 目标或阶段状态。
- 请求：`/v1/completions`，随机输入 16384、输出 1024、并发 64、128 请求；seed 使用现场 vLLM 的默认 0，长度范围 0.0，prefix 长度 0，ignore EOS。
- 相同基础推理配置：TP8、PP1、MBT4096、max-num-seqs64、FP8 KV、block-size256、上下文66560、`FULL_DECODE_ONLY`、编译 mode3、禁用 custom all-reduce、`--no-enable-prefix-caching`。
- 每端一轮无 profiler 预热、一轮采集。torch profiler 跳过 16 个 worker step，`max_iterations=8`；关闭 stack、shape、memory 记录和前端 profiler。
- 两端各 8 份 trace；每份含 8 个完整 `execute_new_*_cached_*` step，GPU kernel 均为 35892 个，correlation ID 能关联 35836 个（99.84%）到 step。
- 丢弃首尾 step，比较中间相同的 6 个 step；两端标注顺序一致，每步平均 4483 个 kernel。GPU 时间取区间并集；CPU self time扣除同线程嵌套事件。CPU/GPU 时间存在重叠，不能相加当成端到端时间。

性能 Skill 操作为 `single-scenario`，bundle SHA-256：`3c46ddd2c4d73b11ca324b230d48429c3d4a40d0c82f56f5b27237d8e81bc9ff`。使用仓库原生 `vllm_profile.py` / `perf_common.py`，先 dry-run。仅诊断副本将 trace 归档的 `shutil.copy2` 改成 `copyfile`，避免 103 NFS 的 xattr I/O 错误；保留字节哈希校验，不修改本地 runner、产品源码或依赖。

## 结果与归因

无 profiler 的预热轮，两端均成功 128/128，输入 2097152 token、输出 131072 token。C588-5 为 440.50 秒、5058.38 total tok/s；103 为 382.25 秒、5829.16 total tok/s。本轮 103 吞吐高 15.24%。各一轮，不能把它当作多轮稳态性能验收；此前 CSV 的 27.23% 差距不能直接套用到本轮。

关键路径 rank 0，中间 6 个 step 的算术平均：

| 指标，ms/step | C588-5 | mx-103 | C588-5 − 103 |
| --- | ---: | ---: | ---: |
| CPU 执行标注跨度 | 810.539 | 617.755 | +192.784 |
| GPU 首末 kernel 跨度 | 809.030 | 616.949 | +192.081 |
| 非 MCCL 计算 kernel 区间并集 | 381.365 | 386.602 | −5.237 |
| MCCL kernel 区间并集 | 74.550 | 87.458 | −12.908 |
| 首末 kernel 之间无 kernel 的区间 | 353.115 | 142.889 | +210.226 |

差异主要指向 **CPU 发射与框架 wrapper 开销**。两端实际 kernel 数和主要计算 kernel 一致，C588-5 的计算 kernel 没有整体变慢；step 增量主要来自 rank 0 的无 kernel 区间。该区间不等于精确的 CPU 自耗时，可能包含 launch、同步、调度及少量 memcpy，不能单凭空隙区分 CPU 微架构、NUMA、系统争用和驱动实现。

整个 8-step 捕获窗口内，rank 0 的部分 CPU 事件：

| 事件 | 次数（两端相同） | C588-5 | mx-103 | 口径 |
| --- | ---: | ---: | ---: | --- |
| `mcModuleLaunchKernel` | 31404 | 16.835 µs | 9.441 µs | 每次 runtime 调用平均跨度 |
| `aten::slice` | 26156 | 31.641 µs | 22.202 µs | 每次 CPU self time |
| `aten::empty` | 25626 | 9.366 µs | 5.384 µs | 每次 CPU self time |
| `vllm::deepseek_v4_attention_fl` | 344 | 1.831 ms | 1.436 ms | 每次 CPU self time，非 GPU kernel 延迟 |
| `vllm::sparse_attn_indexer_fl` | 168 | 1.470 ms | 0.980 ms | 每次 CPU self time，非 GPU kernel 延迟 |
| `vllm::moe_forward_shared` | 344 | 1.322 ms | 1.066 ms | 每次 CPU self time，非 GPU kernel 延迟 |

rank 1–7 的计算区间仍接近，但 C588-5 的 MCCL 区间约 379–400 ms/step，103 约 192–199 ms/step；同时 rank 0 的 MCCL 区间并未变慢。这与其他 rank 在 collective 内等待较慢 rank 的推进相符，不能把其 MCCL kernel 时间直接解释为链路传输延迟。AllReduce 算法确有区别：C588-5 为 `RING_SIMPLE`，103 为 `FC8`；rank 0 的 AllReduce 较慢，但 SendRecv 较快，MCCL 合计没有构成本轮主要差异。

GPU 侧 `qk_states`、`pv_replay`、MHC、INT8 MoE GEMM、row-shard indexer 等主要 kernel 的次数相同、耗时接近。优先检查 CPU/NUMA 放置、主线程争用，以及 attention/indexer wrapper 中大量 slice、tensor metadata 和逐次 launch 的成本；本次没有实施 CPU 绑定、算法切换或算子优化，因此不能声称其中某一项优化已被 A/B 验证。

profiler 增加了 CPU instrumentation 开销，trace 中约 31% 的 step 差距不能直接等同无 profiler 端到端差距，也不能宣称移除全部空隙就能获得对应提速。

## 补充：Qwen 对照与 CPU 型号假设

用户进一步提供 C588-5 的 `/data/jinghao/qwen3.6-35B/test/perf_test/benchmark_results/qwen36-35b-opt4` 和 mx-104 的 `/public-flash/jinghao/qwen3.6-35B/test/perf_test/benchmark_results/qwen36-35b-retest`。本次补充仅只读检查；没有重新压测、采集、绑核或重启任何服务。

mx-104 现场 CPU 为 Xeon Platinum 8460Y+，与前述 mx-103 型号一致。两端 Qwen 镜像仓库 digest 均为 `9f420f54d1e6f60d7fa9fc9ba8bc4f7bd68fb79f60b31598273c8a976436517e`。用户指定 CSV 的 SUMMARY 为跳过首轮、平均后两轮，输出1024、并发64、128请求，成功数与 token 总数一致：

| 输入长度 | C588 total tok/s | mx-104 total tok/s | C588 相对 104 |
| --- | ---: | ---: | ---: |
| 1024 | 3037.22 | 3095.10 | −1.87% |
| 16384 | 10656.35 | 10776.42 | −1.11% |
| 32768 | 11111.39 | 10952.51 | +1.45% |
| 65536 | 9609.97 | 9464.27 | +1.54% |

4K 不能直接当作稳定硬件对照：104 的 Run2 为195.48秒、Run3为104.50秒，SUMMARY4812.15 tok/s 混合了明显不同的状态；C588 为6069.86 tok/s。不能静默忽略这个波动，也不能据此认定 C588 硬件更快。

C588 Qwen 的现存服务、09:58启动日志和 launcher 对应 `qwen36-35b-opt4`，为BF16、TP2、MBT8192、FULL_DECODE_ONLY；实际软件为vLLM0.20.2、torch2.8.0+metax3.7.0.7、`/opt/maca-3.7.0`。DeepSeek 则为 W8A8、TP8、MBT4096、vLLM0.24.0/torch2.10、MACA3.8.2。Qwen 对照改变了模型、算子、batch、并行度和软件栈，不能作为仅改变CPU型号的消融实验。104 的原 `qwen36-35b` 容器当前没有推理进程；根目录日志已被14:30后 `qwen36-35b-retest-old` 测试覆盖，不能用现存旧脚本/日志冒充10:39这次CSV的完整启动绑定。

进一步重读已保存 DeepSeek trace，rank0/1 每端各调用26156次 `aten::slice`。下表为完整 CPU event 平均跨度（包括嵌套子事件，与前表 self time 口径不同）：

| Host | rank0 slice | rank1 slice | rank0 empty | rank1 empty |
| --- | ---: | ---: | ---: | ---: |
| C588-5 | 32.882 µs | 14.105 µs | 9.366 µs | 9.249 µs |
| mx-103 | 22.730 µs | 9.970 µs | 5.384 µs | 5.501 µs |

C588 slice 的中位数也有29.22对12.38µs的差距，而不是仅由少数长尾样本拉高；两 rank 的 slice 均没有超过1ms的单次事件。rank0 特定操作较慢在两种CPU上都存在，CPU型号不能单独解释逻辑rank之间的不对称。

已只读核对容器安装的 `vllm/v1/executor/multiproc_executor.py`：`_get_output_rank()` 在当前TP8/PP1下选择rank0；`worker_busy_loop()` 仅由输出rank提交普通推理响应；启用的 async scheduling 通过 `WorkerAsyncOutputCopy` 调用 `enqueue_output()`，进一步调用异步输出的 `get_output()`。Plugin 的 `vllm_fl/worker/model_runner.py::AsyncGPUModelRunnerOutput.get_output()` 包含事件同步、tensor转CPU列表、输出整理；响应队列还需要入队。这证明rank0承担额外输出职责，但不证明这些职责已经解释全部forward内部空隙；线程/GIL争用、NUMA/CPU放置、驱动及profiler效应仍需单变量实验。

因此结论应严格区分：**已定位的是DeepSeek这套配置的CPU供给侧关键路径；尚未证明海光CPU型号是底层根因，也未证明异步输出/GIL就是唯一原因。** Qwen性能接近与此不矛盾：如果某一模型的CPU开销能被设备执行覆盖，较慢的CPU调用不会等比例反映到吞吐。Qwen是否确实属于这一情形尚无同口径trace，不能把这个机制解释当作实测归因。

后续区分实验应先保留DeepSeek的模型/GPU/版本/负载，只改变CPU/NUMA放置，并采用低扰动CPU采样；再单独验证异步输出路径。不能直接把跨模型吞吐相近、或一次profiler内的CPU时长，当作CPU硬件或GIL的因果证明。
