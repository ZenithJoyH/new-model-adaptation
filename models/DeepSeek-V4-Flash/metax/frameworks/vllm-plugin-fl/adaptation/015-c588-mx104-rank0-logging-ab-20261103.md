# DeepSeek：C588 / C550（104）CPU关键路径诊断

## 结论与边界

2026-11-03完成独立诊断。证据最支持：**DeepSeek当前prefill/mixed路径包含大量CPU元数据操作、Python包装和kernel提交；C588平台执行这些调用明显较慢，使其比Qwen这套配置更容易出现主机供给瓶颈。** CPU平台差异有实测支持，不能将全部差距仅按海光/至强型号归因，CPU微架构、频率与驱动运行时的贡献尚未完全拆分。

已验证三个要点：

1. 当前镜像的Plugin只为rank0强制启用FlagGems oplist。`once=True`在handler处过滤，后续调用仍先查找调用位置、创建LogRecord。它解释了rank0的一项明确不对称开销；关闭后C588完整E2E提升3.59%，104提升0.54%，没有消除跨机差距。
2. 同镜像、相同入口和shape下，C588代表性CPU调用比104慢约32%–75%。相同16K短负载中，DeepSeek主线程CPU占用约74%/78%，Qwen约39%/37%；Qwen不是CPU型号的单变量对照，其模型、算子、TP、batch及软件栈均不同。
3. 按GPU本地节点绑定CPU和内存，虽使C588低并发纯prefill吞吐提高11.95%，但完整原负载下降1.10%。**不能把本次E2E差距主要解释为未绑NUMA，也不能把短场景收益外推到高并发。**

本轮没有修改数值算子、vLLM或永久启动配置，没有执行正式精度/适配验收、打包、提交或发布。异步关闭仅做了低并发prefill筛查，未声称已验证其高并发E2E收益。

## rank0为何额外慢

真实安装Plugin为`/opt/vllm-plugin-fl`、HEAD `a696859b9aa528dfd5b21f5da3403fdc16bac4cd`，存在镜像预置dirty改动。`worker.py`无条件设置`should_record = (rank == 0)`，向FlagGems传递`record=should_record,once=True`。安装版只有oplist路径设置，没有关闭记录的CLI/env开关。FlagGems `LogOncePerLocationFilter`位于handler过滤阶段，因而只避免重复写盘，未避免每次调用创建日志对象的CPU成本。

关闭记录的诊断仅临时修改已核实安装Plugin `vllm_fl/worker/worker.py`这一行，调用原launcher启动任务服务；待8worker完成初始化后立即恢复源码原字节。进程记录状态已在初始化决定。保存`worker-before.py`、`worker-after.py`和单hunk `worker.patch`，不将硬编码False交付为产品修复。最终再以原代码重启原配置服务。

## CPU路径差异与模型敏感度

CPU纯日志微基准执行安装logging helper的原始CPU定义，未导入torch/初始化GPU；固定本地CPU98/CPU0，每状态10万次、5组交替，median：C588关闭139.40ns、once记录5480.98ns；104关闭99.56ns、once记录4149.22ns。记录路径C588慢32.1%，证明CPU侧基础调用差异确实存在，不能直接将其比例外推整模型。

算子wrapper采用实际安装FlagGems的`benchmark/base.py::Benchmark.get_latency`、WRAPPER模式、warmup10ms/repetition50ms、5次重复。主线程固定GPU本地CPU，只有本微基准进程的后台线程移到本节点其他物理核；未改服务亲和性。产品从实际安装路径导入，不用PYTHONPATH/其他副本。slice验证shape/stride/alias，add对独立常量参考验证。按operator:F1/F2/E7保留实际入口、同步方式和原始重复值，不新增或调优算子。

## 具体CPU热点与GPU/MCCL解释

DeepSeek完整NUMA预热rank0的763个GIL成功样本中，85个最近Plugin帧位于`reference/impl/activation.py:49::silu_and_mul_with_clamp_torch`，调用`SiluAndMulWithClamp.forward_native`。安装vLLM实现将其展开为slice、clamp、sigmoid、mul、add等ATen操作。Plugin FlagGems adapter在`VLLM_FL_USE_FLAGGEMS_VLLM`未启用时也走native；该变量现场未设置，env默认False。日志标记`default.flagos`不证明已经进入融合kernel，实际栈才是依据。未独立替换此激活做A/B，不能把85/763直接当作E2E耗时或确定优化收益。

此外能看到attention/indexer、mHC、量化、Triton dispatch/launch等CPU调用。其组成与Qwen明显不同。Qwen安装Plugin的普通`silu_and_mul`接入`gems_silu_and_mul`；两模型也都启用了rank0 oplist，不能解释成“Qwen没有开日志”。

[014多rank记录](014-c588-c550-prefill-profile-20261103.md)是在迁移前C588/103采集的全部8rank trace，不是104的新trace：匹配中间6个长输入step，每步4483个kernel，rank0非MCCL计算区间约381/387ms，而无kernel区间约353/143ms；rank0 MCCL区间约75/87ms，其他rank在C588的MCCL显著变长。这符合较慢rank推进使其他rank在collective中等待，不能将MCCL kernel跨度直接当作链路传输耗时。该Torch profiler有CPU扰动，不能用这些区间直接折算无profiler E2E差距。

Qwen历史16K总吞吐C588/104为10656.35/10776.42tok/s，相差约1.1%。Qwen实际TP2、BF16、MBT8192、vLLM0.20.2/torch2.8/MACA3.7；DeepSeek为TP8、W8A8、MBT4096、vLLM0.24/torch2.10/MACA3.8.2。两者都用FULL_DECODE_ONLY，不能用“Qwen开了完整prefill图而DeepSeek没开”解释。实际主机负担和算子链路不同；现有证据符合Qwen CPU开销更容易被设备执行覆盖的机制，但未采集同口径Qwen GPU trace，不能声称已逐kernel证明其全部瓶颈。
