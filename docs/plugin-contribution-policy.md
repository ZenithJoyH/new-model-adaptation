# vllm-plugin-FL 修改与 PR 交付标准

这是本项目对适配代码的交付要求。每次修改应符合插件的整体设计，保持已有模型和平台
的行为，并让上游审查者能理解问题、设计选择和验证范围。实际能否合并由上游维护者决定。

修改前阅读目标插件 checkout 中的 AGENTS/贡献指南、架构/dispatch 文档、相关实现、
调用方和正常测试入口，并记录 revision。[本地架构分析](vllm-plugin-FL-analysis.md) 是
固定 revision 的参考，不能代替当前源码。本文不授权额外修改 vLLM、共享源码或无关工作负载。

## 1. 先确定职责与边界

在平台环境分析或对应编号适配问题中为每项实质变更写明：问题的完整签名、
现有调用链、候选扩展点、所选层级及原因、影响面和验证计划。优先沿用现有可维护的路径；
选择改动面时同时考虑职责、语义和复用，不以代码行数最少作为唯一目标。

| 变更语义 | 应归属的位置或扩展点 | 必须检查的边界 |
|---|---|---|
| 模型结构、权重映射、特定架构协议 | model/config/shim 与正式 registry | 复用上游可用实现；行为按架构/能力约束 |
| vLLM 层接口接入 | OOT、工厂或现有注册接口 | 调用实际进入 plugin，输入输出与上游契约一致 |
| 同一语义的多实现选择 | 已有 dispatch/backend/policy | 所有适用调用方采用统一选择路径与诊断机制 |
| 芯片、驱动或厂商 SDK 限制 | 相应 vendor backend、能力判断与局部策略 | 其他平台导入及默认行为不依赖该 SDK |
| dtype、layout、量化、cache 协议 | 对应 adapter、量化或 attention 层 | 不为单一 backend 偷改所有调用方的公共契约 |
| 调度、graph、worker 公共语义 | 现有引擎扩展层，需证明问题属于这一层 | 逐项检查共享模型、平台和并行执行路径 |

模型确有独特语义时允许专用实现和准确注册，不要用模型目录名、服务名称或权重路径
在公共 worker、dispatch、graph 热路径里分支。硬件特例按设备/软件能力、dtype、shape、
layout、量化或拓扑等真实触发条件限制，不将一次故障推广为平台的永久全局限制。

只有现有扩展点无法表达必要行为时才引入新的抽象，并说明现有设计的不足、实际调用方、
接口和测试。暂时只有一个使用方可以是合理实现，但不得宣称已验证跨模型/平台通用性，
也不为假想需求增加新的注册系统、执行框架或参数层。

## 2. 保持接口和初始化行为

- 明确算子/组件的 dtype、shape、stride、layout、device、返回值、out/in-place/view/alias、
  workspace、空输入、边界条件及错误行为；需要时验证 fake/meta、编译器和 custom-op schema。
- 公共入口使用既有 dispatch 选择实现；backend adapter 在该边界内调用 FlagGems 或
  vendor API 属于正常集成。不得从模型或通用调度层绕开选择机制另接一条临时路径。
- 可选厂商依赖惰性加载，只在相关能力被选择后初始化；导入插件、模型注册和 CPU 检查
  不应要求无关 SDK、加载无关动态库、分配设备显存或修改全局设备状态。
- 注册和兼容 hook 要幂等，覆盖 fresh process、spawn worker 和重复初始化；不得通过
  宽泛异常捕获或伪造空实现掩盖缺失能力、真实初始化错误或 ABI 不兼容。
- 不同配置、模型/平台选择及 policy 变化后的缓存必须正确失效，不能复用错误实现。
- 不复制整套上游模型、worker 或 backend 以取得一个局部修复；确需复用代码时说明来源、
  许可证、不可复用现有接口的原因和后续维护方式。构建依赖/原生扩展必须有可复现来源，
  不将某台机器上的预编译 .so、绝对路径或一次性环境信息作为通用方案。

## 3. 特例、fallback 与 workaround

每个特例记录适用模型结构、平台、软件版本/能力、dtype/shape/执行模式及不适用条件。
测试条件成立时进入新路径，也测试条件不成立时保留原有路径。

优先在执行前判断不支持的能力，并使用框架已有的 fallback。已有异常回退机制仍按其
设计使用，但不得扩大为捕获任意异常后静默切换：OOM、rank 异常、通信错误、已发生的
in-place/cache 修改或 collective 不能假定可以安全重试。数值错误必须通过对照测试发现。
诊断时固定/严格选择目标实现，证明命中；随后验证正常生产 policy 和可观测的 fallback。

临时 blacklist、native/reference 回退、版本 hook、graph 降级或超时调整必须记录：
触发证据、最小作用域、数值/性能影响、限制、上游缺陷或待修位置、移除条件和验证方法。
支持受控的 workaround 作为明确披露的 PR 内容，不把它描述成已经解决根因；不得为了
当前模型未经论证地更改所有模型/平台的 backend 优先级、禁用项或 graph 默认值。

## 4. 按影响面验证多模型、多平台

在计划中建立矩阵，列出受影响共享符号和调用方，而非机械要求所有模型乘所有设备。
至少考虑新路径、相关已有路径和不应受影响的路径；相同依赖链可以选择有依据的代表用例。

| 修改类型 | 必需的针对性验证 |
|---|---|
| 模型专用 shim/注册 | 目标架构与权重协议；已有模型注册不变；守卫未命中场景 |
| 公共算子、dispatch、量化或 attention | 目标模型，以及受影响的已有调用方/代表模型；原 backend 与新 backend 的选择和数值对照 |
| vendor 实现/平台策略 | 目标设备实际 eager/graph；另一平台或无该 SDK 环境的导入、注册、选择隔离；守卫两侧 |
| 初始化、缓存、worker、scheduler、graph 公共层 | 无设备导入（适用时）、spawn/重复注册、配置切换，以及受影响模型结构与并行拓扑 |

有状态路径覆盖 prefill/decode、chunked/mixed batch、cache 更新、空/边界输入；涉及 graph 时
覆盖 warmup、capture、至少两次变输入 replay，防止复用旧输出或失效地址。并行路径关注
rank 一致分支、collective 顺序、异步错误和输出所有权。

修复测试应在变更前复现问题，并在变更后通过；不便运行旧实现时保留可靠的负对照及原因。
测试进入插件现有测试体系，断言行为和数值，不靠搜源码字符串、mock 掉目标计算、宽泛
skip/xfail 或放宽容差来证明成功。mock 适用于依赖隔离/选择逻辑，不替代设备数值或 graph 测试。

缺少其他平台硬件时，先完成能运行的契约/隔离测试，再列明未执行的实际平台测试及影响。
这不自动要求扩展到未授权主机，也不能声称那些平台已验证。已知回归必须修复或缩小改动
作用域；重大未验证风险必须在审查和 PR 限制中显式呈现。

正式精度和性能仍遵循五阶段顺序；本节的局部回归不替代完整验收，也不要求重复完整 eager
精度/性能测试。性能声明必须有同条件基线、实际 backend 命中及目标指标。

## 5. 交付最终 diff 的设计审查

在阶段 3 收尾、实质变更后以及准备 PR 前，在对应编号适配问题和最终验收总结中记录设计
审查。最终检查对准真实 checkout：

1. 记录目标 repository、已确认的 PR base branch/revision、当前 HEAD，以及本任务开始前
   的 dirty 状态。目标分支未确认时记录缺项，不自行假定 main。
2. 区分相对 PR base 的完整变更与本任务新增差异，列出 inherited diff、提交、暂存/未暂存
   和新增文件；只看 HEAD 或 `git diff` 不能覆盖全部内容。记录 diff hash/清单定位实际代码。
3. 逐文件解释职责、必要性、现有调用方、接口/默认值变化、兼容性证据及替代方案。
4. 按第 4 节给出已执行/未执行/不适用及依据，检查是否有绕开 dispatch、泄漏平台依赖、
   重复实现、吞异常、无效断言或未清理的试验残留。
5. 给出明确结论：可作为 PR 候选 / 需修改 / 无插件变更。记录阻塞问题和待验证项；
   修改代码后重新审查受影响部分并更新绑定信息，旧审查不能覆盖新的 HEAD 或 dirty diff。

“可作为 PR 候选”表示设计审查满足声明的范围，不意味着所有硬件或完整适配已验收。
设计审查未通过时不能将阶段 3 标记完成；完整验收状态和 PR 设计审查状态分别记录。
没有插件变更也要给出范围核对依据，不能把插件配置变更当作没有变更。

准备给用户的 PR 材料包括问题与前后行为、设计理由、影响矩阵、精确验证环境和命令、
实际结果、兼容/性能限制及 workaround 退出条件。修改保持主题集中；可独立验证的公共
修复与模型适配可建议拆 PR，无关重构留作后续。不要仅为整理 diff 擅自提交、改写历史、
处理用户的既有改动或推送；用户明确要求后再执行相应 Git/PR 操作。

本地脚手架和文件检查只能辅助确认材料齐备，不能自动判定架构设计合理或上游一定会接受。
适配阶段的证据绑定包含设计审查记录；缺失或内容变化会使旧绑定失效。真实源码变化时，
仍必须核实 HEAD、dirty/新增文件和运行配置并更新审查，不能依赖文档哈希检测远端代码变化。
