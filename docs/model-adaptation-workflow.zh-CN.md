# 新模型适配通用工作流

五阶段用于组织工作，不规定所有框架采用同一种实现或测试方法。实际步骤由所选 profile 的
workflow、acceptance 文档、有序 `acceptance.steps`、适用平台、可写组件和执行模式决定。

- `draft`：仅模型分析和只读环境调查。
- `experimental`：允许在已批准任务范围内实施适配、执行明确声明的验证子步骤；尚不能完成正式验收。
- `active`：已定义完整验收能力，可以按流程执行；不代表具体模型已通过。
- vllm-plugin-fl 和 Torch-FL 分别维护自己的实施流程与验收标准。

## 工作区与修改边界

每个模型、平台、框架和 Host 使用独立批准远端根目录。写入前核实 Host、容器身份、
`host_root`、`container_root` 与实际映射；评测容器单独核实。每条命令指定 workdir，
cd 失败停止，检查 symlink 和隐式写入。按顺序使用 `01-environment/`、
`02-issues/`、`03-acceptance/`、`04-runs/`、`05-tmp/`、`06-cache/`、
`07-bugs/`。不得建立源码镜像或把原始远端产物批量搬回本地。

产品修改仅进入已核实身份且 profile 声明可写的源码；保留既有工作。适配容器必须保持运行；
可在核实身份后停启本任务服务或进程。外部权重、数据集、依赖保持只读，源码同步仍需既有
授权。旧目录迁移须核实使用方和证据并获得用户迁移授权。`07-bugs/` 中已有用例原地执行；
上游确需 `/bug` 时仅通过已批准映射暴露同一目录。

本地记录位于 `models/<model>/<platform>/frameworks/<framework>/`，三个子目录仅放
Markdown 环境分析、编号问题、验收与复盘文档。可执行配置和完整测试产物留在远端。

## 1. 模型结构与推理链路分析

模型级 `architecture-and-inference.md` 使用中文，分析整体结构、配置、张量与数据流、
推理阶段、并行策略及实际关键算子，区分已验证事实、假设和待确认项。框架特有执行链路
放在对应框架记录中。

## 2. 推理环境分析

仅分析用户指定平台和 Host。记录硬件拓扑、容器、驱动、工具链、包与源码身份、revision、
资源、根目录映射和兼容性缺口。变更前搜索已验证经验，并在当前环境重新核实适用性。

## 3. 进行适配

结合模型分析、环境分析与用户参考资料，按 profile 的具体子步骤实施。建立基线，一次改变
一个关键变量；复用框架扩展点、逐层测试、记录问题和最终 diff 审查。过程代码放在产品源码
之外。vllm-plugin-fl 使用 Plugin/FlagGems 接入流程；Torch-FL 使用设备、dispatch/backend、
厂商运行库集成与可选 wheel 构建流程。

## 4. 适配验收

按所选 profile 声明的顺序执行用户选择的子步骤，并核验前置证据。可选步骤在运行前显式
加入工作区有序 substeps。缺少 runner 或未实现的能力不得猜测或判通过。

正式精度按冻结阈值、完整有效样本及原生结果判定，允许题目答错、超时计失败。Markdown
哈希不能替代正式回执。前缀缓存按框架能力处理；适用时性能专用服务必须关闭缓存，Python
API 测试不能套用 vLLM 启动参数。

active 框架完整服务适配交付前，逐 Host 核实根目录 `start-model.sh` 的主执行模式、
运行身份、可执行性、语法、实际就绪、最小必要参数、正常缓存状态和容器映射。
日志/结果写 `04-runs/`，缓存写 `06-cache/`；本地记录准确路径、SHA-256 和验证日期。
脚本不得停启容器。实验性 Torch-FL 可以完成独立验证项并达到 `functional`，
不能宣称全量精度、性能、`optimized` 或正式整体验收已经完成。

## 5. 适配复盘

回顾本次选定工作的已验证问题、方案、无效尝试、限制和流程改进。实验性工作也可以复盘，
无需把未完成的正式验收标为通过。只提升有复验依据的可复用经验，注明 revision 和适用范围；
通用仓库规则修改仍须对应用户请求。

证据格式与命令见 [框架证据契约](framework-evidence.md) 和 [操作指南](workflow-guide.md)。
本地审计不执行远端核验，也不证明服务当前仍然可用。
