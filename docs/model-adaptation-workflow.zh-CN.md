# 新模型适配通用工作流

五阶段用于组织工作，不规定所有框架采用同一种实现或测试方法。实际步骤由所选 profile 的
workflow、acceptance 文档、有序 `acceptance.steps`、适用平台、可写组件和执行模式决定。

- `draft`：仅模型分析和只读环境调查。
- `experimental`：允许在已批准任务范围内实施适配、执行明确声明的验证子步骤；尚不能完成正式验收。
- `active`：已定义完整验收能力，可以按流程执行；不代表具体模型已通过。
- vllm-plugin-fl 和 Torch-FL 分别维护自己的实施流程与验收标准。

## 工作区与修改边界

每个模型、平台、框架和 Host 使用独立批准远端根目录。写入前核实 Host、容器身份、
`host_root`、`container_root` 与实际映射；评测容器单独核实。每条命令指定 workdir，
cd 失败停止，检查 symlink 和隐式写入。按顺序使用 `01-environment/`、
`02-issues/`、`03-acceptance/`、`04-runs/`、`05-tmp/`、`06-cache/`、
`07-bugs/`。不得建立源码镜像或把原始远端产物批量搬回本地。

产品修改直接进入已核实且 profile 声明可写的容器实际安装组件/源码；禁止用 `PYTHONPATH`
或其他导入覆盖选择另一版本，记录包/import 身份及 Git diff 或安装文件哈希，保留既有工作。
适配容器必须保持运行；可在核实身份后停启本任务服务或进程。可写范围外的依赖以及
外部权重、数据集保持只读，源码同步仍需既有
授权。旧目录迁移须核实使用方和证据并获得用户迁移授权。`07-bugs/` 中已有用例原地执行；
上游确需 `/bug` 时仅通过已批准映射暴露同一目录。

本地记录位于 `models/<model>/<platform>/frameworks/<framework>/`，三个子目录仅放
Markdown 环境分析、编号问题、验收与复盘文档。可执行配置和完整测试产物留在远端。

执行所选阶段前按[规范与门槛规则](adaptation-policy.zh-CN.md#规范优先级文档缺失与阶段门槛)
裁定适用要求。已核实的阅读材料缺失记录替代依据，不单独阻塞已授权实施；契约/写入边界
不明确时暂停受影响修改，检查失败或未执行时阻塞对应验收/交付声明，可继续获准的定位。
显式适用说明仅覆盖指明冲突，其余硬性要求和所选 profile 的阶段顺序继续执行。

## 1. 模型结构与推理链路分析

模型级 `architecture-and-inference.md` 使用中文，分析整体结构、配置、张量与数据流、
推理阶段、并行策略及实际关键算子，区分已验证事实、假设和待确认项。框架特有执行链路
放在对应框架记录中。

## 2. 推理环境分析

仅分析用户指定平台和 Host。记录硬件拓扑、容器、驱动、工具链、包与源码身份、revision、
资源、根目录映射和兼容性缺口。变更前搜索已验证经验，并在当前环境重新核实适用性。

### 沐曦多机通信预检

沐曦适配涉及两台及以上 Host 时，阶段 2 先使用
[MetaX-MACA/mccl_tests](https://github.com/MetaX-MACA/mccl_tests) 检查跨机通信，
通过后再运行依赖该通信的多机模型。这是适用框架共用的环境前提，不新增阶段，也不是
模型正式性能验收。单机适配不强制跨机测试；未选择阶段 2 时只检查准确匹配的已有证据，
缺少证据不等于获准补跑未选阶段。draft/只读 profile 的限制仍然有效。

1. **核实范围与运行环境。** 确定准确 Host、分配的 GPU、批准根目录及容器映射。
   在实际适配容器中使用与模型运行相同的 MACA/MCCL 库测试，记录 SDK、驱动、MPI、
   实际加载的 MCCL 版本/路径、测试 revision、二进制路径/哈希、rank/GPU 映射、网卡及
   RDMA 设备。检查跨机进程拉起和设备可见性，保留无关服务并保持适配容器运行。
   不隐含授权安装/升级 SDK、修改 SSH/网络策略或扩大资源使用范围。
   所有测试 rank（包括 MPI 跨机拉起的进程）必须运行在各自对应的实际适配容器内；
   仅在主节点容器内启动 `mpirun` 不能证明远端 rank 也进入了容器。逐 Host 记录容器 ID、
   rank 进程及容器归属、实际加载库、GPU/RDMA 设备映射和网络模式，并与模型运行所用
   配置一致；不得换成独立测试容器或宿主机库获取通过结果。允许在授权范围内由宿主机
   编排进入容器的启动动作，但宿主机 benchmark 只能用于辅助定位，不能替代容器预检。
   若远端 rank 落在宿主机或容器归属无法核实，预检保持未完成，修复启动路径后重测。
2. **核实启动命令。** 使用前阅读固定版本的 README、编译和启动脚本。已审阅的上游
   `cluster.sh` 实际接收 `"IP1:slots,IP2:slots"`、总进程数、测试名，与 README 旧参数
   描述不同；默认程序位于 SDK samples，HCA 名称写死且网段按 `/24` 推算。必须按现场
   核实程序和每台 Host 实际加载的库、网卡及网段，不照搬示例 IP/NIC 或默认值；新版需重查。
3. **逐步覆盖目标拓扑。** 按各机单机多卡 → 双机各一卡 → 多机多卡的顺序，覆盖计划中的
   rank 组。测试 AllReduce 及模型并行实际需要的操作，例如 TP 的 AllGather/ReduceScatter、
   PP 的 Send/Recv、EP 的 All-to-All。扫描小/大消息，开启正确性检查（`-c 1`）、预热和
   重复迭代；记录 dtype、消息范围、次数、时延、`algbw`、`busbw` 和错误。根据运行证据
   核实实际传输方式及网卡路径，MPI 作业完成不能单独证明使用了 RDMA 或目标路径正常。
4. **形成结论。** 所选检查全部完成、结果正确、无挂起/超时且使用预期通信路径才可通过。
   根据链路/拓扑事实或可比基线定位明显带宽与延迟异常，不凭空规定统一带宽阈值，也不把
   `busbw` 当作网卡原始吞吐。失败、未测或异常未解决时，该环境前提保持未完成，阻塞
   依赖该通信的多机运行；独立分析及获准定位可继续。仅复用范围匹配的已核实证据，Host、
   拓扑、容器、通信库或网络配置变化后重测受影响项，不静默改写历史验收状态。

测试配置/命令放在批准远端根目录的 `01-environment/`，测试源码/编译产物放在声明的
`05-tmp/` 子目录，完整输出放 `04-runs/`；不混入 Plugin/算子源码或本地模型目录。
本地 `environment/environment-analysis.md` 仅记录范围、命令、版本、结果、阻塞项及
远端证据准确路径/哈希。本预检可先于模型精度测试执行，不需要模型服务、启动脚本或
前缀缓存切换；通过不代表框架 TP/PP/EP 接入或 graph capture/replay 已通过，后续仍按
所选 profile 完成 graph、精度与性能验收。

## 3. 进行适配

结合模型分析、环境分析与用户参考资料，按 profile 的具体子步骤实施。建立基线，一次改变
一个关键变量；复用框架扩展点、逐层测试、记录问题和最终 diff 审查。过程代码放在产品源码
之外。vllm-plugin-fl 使用 Plugin/FlagGems 接入流程；Torch-FL 使用设备、dispatch/backend、
厂商运行库集成与可选 wheel 构建流程。

算子修改同时遵循[算子层开发规范](operator-development-standard.md)的适用条款及用户澄清：
FlagGems 仅提供 ATen 自动替换；vLLM 算子（包括非 ATen 融合计算）由 FlagGems-vllm 提供。
验证契约、独立数值、真实分发和适用的
图执行/autotune 状态恢复。组件 benchmark 在本阶段按算子仓库准入执行，不要求预设
整模型速度目标；证据并入现有源码审查。

## 4. 适配验收

按所选 profile 声明的顺序执行用户选择的子步骤，并核验前置证据。可选步骤在运行前显式
加入工作区有序 substeps。缺少 runner 或未实现的能力不得猜测或判通过。

profile 声明图模式优先顺序时，必须按序尝试。当前 vLLM profile 使用以下项目尝试顺序，
不把它视为必然的性能排名：

| 记录值 | vLLM 模式 | 图覆盖范围 |
| --- | --- | --- |
| `full` | `FULL` | prefill/mixed 和兼容 decode 批次的全图。 |
| `full-and-piecewise` | `FULL_AND_PIECEWISE` | decode 全图，prefill/mixed 分段图。 |
| `decode-full` | `FULL_DECODE_ONLY` | decode 全图，prefill/mixed 不使用图。 |
| `piecewise` | `PIECEWISE` | 分段图，不支持入图的算子在图外运行。 |

模式含义参考 [vLLM 官方图文档](https://docs.vllm.ai/en/latest/design/cuda_graphs/)，使用前核实
实际安装版本、backend、编译前置和参数名称。其他框架声明自己的支持顺序，不套用 vLLM
枚举。每次回退前先定位并尝试解决当前档位问题，记录配置、可复现失败、修复尝试、仍未
解决的阻塞、限制、证据和恢复尝试条件；不能一报错就降级，也不能跳级。确证某版本或
backend 不支持某档位时，可用源码/能力证据记录，不要求反复无效启动，但不能省略该级记录。

目标是正确、稳定前提下的性能表现。对可运行候选，在相同 workload、拓扑、上下文长度和
缓存状态下记录吞吐、TTFT/逐 token 时延及显存；不能假定图覆盖越高性能必然越好。
性能阻塞也需要受控对比和优化尝试，不能凭猜测回退；正式性能测试仍在精度通过后执行。
检查实际启动配置和 capture/replay 证据：框架自动降级不等于原档位通过。
只有每个更高档位都有阻塞证据，`piecewise` 才可验收；全部图模式失败时，eager/NONE
仅用于诊断，graph 验收保持未完成。后续回执和启动脚本绑定逐 Host 最终验证模式；
更换模式须使受影响证据失效并重新验证，包括先精度、后正式性能，不得静默切换。

服务小批量预检发送代表性文本请求；图像模型另发图像请求，逐项审阅切题、乱码、空输出、
异常重复和实际图像理解，不要求开放式回答逐字匹配。保留原始响应、时延及绑定结果的审阅
结论；明显性能问题先修复再做正式精度。随后性能验收要求完整有效实测，不强制预设速度
目标；只有用户明确要求并配置的量化优化目标才额外检查目标达成。首次测量无需已有基线，
比较收益或相对目标才需要基线。小批量前按[服务证据契约](evidence-contract-v2.md#服务范围与共享启动绑定)
冻结实际模型能力、结构分析哈希、服务别名及逐 Host 启动配置，不能仅改请求清单来减少模态覆盖。

正式精度按冻结阈值、完整有效样本及原生结果判定，允许题目答错、超时计失败。Markdown
哈希不能替代正式回执。前缀缓存按框架能力处理；适用时性能专用服务必须关闭缓存，Python
API 测试不能套用 vLLM 启动参数。

服务型 profile 在小批量/正式验收前准备最小的根级 `start-model.sh`，精度与性能均复用
同一脚本，仅显式性能开关关闭前缀缓存，交付保留这份已测脚本。每轮绑定共享脚本哈希、
实际进程 argv、必要环境变量及有效配置快照；除缓存外变更须重新验收。按
[统一服务启动入口](remote-operations.zh-CN.md#统一服务启动入口)删除非必要缓存目录覆盖，
记录已核实的默认路径；不为纯 Python API profile 添加服务脚本。
active 框架完整服务适配交付前，逐 Host 核实根目录 `start-model.sh` 的主执行模式、
运行身份、可执行性、语法、实际就绪、最小必要参数、正常缓存状态和容器映射。
日志/结果写 `04-runs/`，评测缓存写 `06-cache/`，服务运行时默认缓存按统一入口规则处理；
本地记录准确路径、SHA-256 和验证日期。
脚本只保留必要启动指令与设置，诊断/就绪检查在验收时单独执行。按
[镜像交付要求](remote-operations.zh-CN.md)核实必需文件会随镜像保留在容器路径，
不依赖临时宿主挂载或导入覆盖；真正完成打包及新容器测试后才能记录镜像验证通过。
脚本不得停启容器。实验性 Torch-FL 可以完成独立验证项并达到 `functional`，
不能宣称全量精度、性能、`optimized` 或正式整体验收已经完成。

## 5. 适配复盘

回顾本次选定工作的已验证问题、方案、无效尝试、限制和流程改进。失败、阻塞、部分完成
及实验性任务都可单独复盘，不要求前序验收通过。复盘上下文绑定实际阶段状态与证据；
状态变化须重新复核，复盘通过不代表适配或验收通过。只提升有复验依据的可复用经验，注明 revision 和适用范围；
通用仓库规则修改仍须对应用户请求。

## 完成交付：英文部署文档

每次适配完成必要验收及本次选定的复盘后，Agent 必须在最终交付前调用
[adaptation-deployment-guide](../skills/adaptation-deployment-guide/SKILL.md)。该 Skill 现支持镜像
发布与部署；除非任务已包含这些操作，默认完成交付仍只生成文档，不新增第六阶段，也不
允许补跑未选阶段。在准确的本地框架工作区（历史记录沿用
平台工作区）生成英文 `acceptance/deployment-guide.md`，仅使用 Skill 内维护的模板。
它面向部署使用者，与内部适配总结分开保留。模型权重下载章节仅作为说明，不执行下载。
部署、启动、评测、打包、发布和许可证均依据已有可核验证据，缺失内容明确标记待确认。

同一 Skill 可单独选择：仅生成文档、本地打包验证、发布并部署，或部署已有镜像。
文档模式只读已有记录，不操作远端或重跑测试。发布模式按所选范围执行内容审查、独立候选
整理、本地验证、推送及已发布镜像四步部署；保持适配源容器运行，复用已验收的最小
`start-model.sh`，会话管理和就绪检查放在脚本之外。候选、发布、部署及正式服务状态分别记录，
部署冒烟验证不替代正式精度/性能验收，也不授权修改工作流状态。
部分完成或 experimental 工作只能生成明确标注的草稿，不能宣称整体验收完成。文档缺失
或仍为草稿时报告文档交付未完成，不改写技术验收结果。这是 Agent 的调用要求，不新增
原生回执、后台任务或可执行 hook。

证据格式与命令见 [框架证据契约](framework-evidence.md) 和 [操作指南](workflow-guide.md)。
本地审计不执行远端核验，也不证明服务当前仍然可用。
